# MicroFleet

Тёмное desktop-приложение на PySide6 для управления bash-скриптами микросервисов на Linux-серверах по SSH.

## Возможности первого релиза

- серверы, группы/зеркала и микросервисы хранятся локально в SQLite;
- подключение по SSH-ключу, ssh-agent или паролю;
- переключение в login-окружение отдельного пользователя через `sudo su - USER`;
- общий управляющий скрипт для каждого сервера с действиями `start`, `stop`, `restart`, `status` для выбранного сервиса или `all`;
- постоянная интерактивная SSH-сессия с баннером, prompt и потоковым выводом;
- отображение ANSI-цветов терминала, включая 256-цветные и RGB-последовательности;
- отдельный буфер терминала для каждого сервера;
- извлечение статусов микросервисов из ответа общего скрипта и показ в таблице;
- произвольная shell-команда в активной SSH-сессии;
- отправка `Ctrl+C` для остановки длительной команды;
- SSH-пароль хранится только в памяти текущего процесса.

## Запуск

Требуется Python 3.11 или новее.

```powershell
py -3.11 -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -e .
microfleet
```

Либо после установки зависимостей:

```powershell
python -m microfleet
```

База создаётся автоматически в системном каталоге данных приложения (`QStandardPaths.AppDataLocation`).

## Ожидания от удалённого сервера

После SSH-подключения приложение выполняет в терминале:

```text
sudo su - <run_as_user>
```

После смены пользователя команды микросервисов отправляются в ту же интерактивную сессию. SSH-пользователь должен иметь право выполнить `sudo su - <run_as_user>` без запроса пароля. Для production рекомендуется ограничить права `sudoers` нужным пользователем. Ключ нового SSH-хоста при первом подключении принимается на время работы клиента; для строгой инфраструктуры заранее добавьте ключи серверов в системный `known_hosts`.

В параметрах каждого сервера укажите путь к общему скрипту, например `/opt/apps/manage.sh`. У микросервиса задайте точное имя, которое ожидает скрипт. Кнопка сервиса отправляет команду вида:

```bash
/opt/apps/manage.sh restart billing-api
```

Кнопки «Все» отправляют тот же скрипт с аргументом `all`, например `/opt/apps/manage.sh status all`. Массовые `start`, `stop` и `restart` требуют подтверждения.

При подключении приложение запрашивает `status all`. После `start`, `stop` или `restart` оно повторно запрашивает `status` для затронутого сервиса (или `status all`). Основной ожидаемый формат ответа: `Checking service "issuing-service" ..... running.` — количество пробелов не важно. Для `status all` такая строка должна выводиться для каждого сервиса. Поддерживаются `running`, `stopped`, `failed` и `not running`; также распознаются некоторые другие английские и русские формулировки. Неизвестный формат отображается в таблице как «Неизвестно».

В SSH-консоли показываются понятная команда управления и её вывод. Служебные `printf`-маркеры, которыми приложение отделяет вывод и код завершения команды, скрываются из отображения.

При первом запуске после обновления старая SQLite-база автоматически получит поле общего скрипта. Существующие серверы и микросервисы сохранятся; путь к общему скрипту нужно заполнить в параметрах сервера. Старые индивидуальные пути остаются в базе для сохранности данных, но больше не используются.
