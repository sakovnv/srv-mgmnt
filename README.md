# MicroFleet

Тёмное desktop-приложение на PySide6 для управления bash-скриптами микросервисов на Linux-серверах по SSH.

## Возможности первого релиза

- серверы, группы/зеркала и микросервисы хранятся локально в SQLite;
- подключение по SSH-ключу, ssh-agent или паролю;
- переключение в login-окружение отдельного пользователя через `sudo su - USER`;
- общий управляющий скрипт для каждого сервера с действиями `start`, `stop`, `restart`, `status` для выбранного сервиса или `all`;
- постоянная интерактивная SSH-сессия с баннером, prompt и потоковым выводом;
- отображение ANSI-цветов терминала, включая 256-цветные и RGB-последовательности;
- отдельный буфер терминала для каждого сервера;
- извлечение статусов микросервисов из ответа общего скрипта и показ в таблице;
- произвольная shell-команда в активной SSH-сессии;
- отправка `Ctrl+C` для остановки длительной команды;
- на Windows SSH-пароль может сохраняться в системном Диспетчере учётных данных для текущего пользователя; в SQLite пароль не записывается.
- общий для всех серверов DEK-пароль текущего пользователя может сохраняться там же; при `start`/`restart` приложение отвечает на два приглашения скрипта автоматически.

## Запуск

Требуется Python 3.11 или новее.

```powershell
py -3.11 -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -e .
microfleet
```

Либо после установки зависимостей:

```powershell
python -m microfleet
```

Список серверов, микросервисы и остальные настройки сохраняются в SQLite рядом с приложением: `config/users/<домен_пользователь>-<идентификатор>/microfleet.db`. Для каждого пользователя Windows создаётся своя папка. При первом запуске после обновления база из прежнего пользовательского `AppData` копируется автоматически; исходный файл остаётся на месте. Приложению нужны права записи в `config/users` рядом с `.exe` — установка в защищённую папку вроде `Program Files` без настройки прав не подойдёт. Разделение папок само по себе не ограничивает чтение: на терминальном сервере администратор должен настроить NTFS-права для пользовательских каталогов. Для тестов и администрирования путь можно переопределить переменной `MICROFLEET_DB_PATH`.

При выборе авторизации по паролю оставьте включённым флажок «Сохранять в Диспетчере учётных данных Windows». В следующий запуск пароль загрузится автоматически. Поле пароля при редактировании сервера остаётся пустым: это не удаляет сохранённый пароль. Чтобы заменить его, введите новый; чтобы удалить — снимите флажок и сохраните параметры. Сохранённая запись также удаляется при удалении сервера. При смене адреса, порта или SSH-пользователя старый пароль не переносится автоматически. При переносе базы из прежнего `AppData` приложение также переносит доступные этому пользователю записи паролей. Пароль доступен только из той же учётной записи Windows на этом компьютере; перенос одного файла SQLite на другой компьютер его не переносит. На других ОС пароль остаётся только в памяти до закрытия приложения.

Кнопка «DEK-пароль» внизу списка серверов задаёт один полный пароль для текущего пользователя и всех его серверов. Он хранится отдельно от SSH-паролей и не записывается в SQLite. При `start`/`restart` пароль делится пополам (при нечётной длине первый компонент длиннее на один символ). После приглашений `Enter first password component:` и `Enter second password component:` приложение отправляет соответствующие части; эхо ввода временно отключается, а возможное отражение секрета в выводе скрывается. Последующий `status` выполняется после завершения действия, поэтому его команда не попадёт в запрос пароля. При отсутствии DEK-пароля автоматический ответ не отправляется. На Windows выбранный DEK сохраняется в Диспетчере учётных данных текущего пользователя, на других ОС — только в памяти процесса.

## Ожидания от удалённого сервера

После SSH-подключения приложение выполняет в терминале:

```text
sudo su - <run_as_user>
```

Команды микросервисов выполняются в той же интерактивной SSH-сессии после `sudo su - <run_as_user>`. SSH-пользователь должен иметь право выполнить `sudo su - <run_as_user>` без запроса пароля. Для production рекомендуется ограничить права `sudoers` нужным пользователем. Ключ нового SSH-хоста при первом подключении принимается на время работы клиента; для строгой инфраструктуры заранее добавьте ключи серверов в системный `known_hosts`.

В параметрах каждого сервера укажите путь к общему скрипту, например `/opt/apps/manage.sh`. У микросервиса задайте точное имя, которое ожидает скрипт. Кнопка сервиса отправляет команду вида:

```bash
/opt/apps/manage.sh restart billing-api
```

Кнопки «Все» отправляют тот же скрипт с аргументом `all`, например `/opt/apps/manage.sh status all`. Массовые `start`, `stop` и `restart` требуют подтверждения.

При подключении приложение запрашивает `status all`. После `start`, `stop` или `restart` оно повторно запрашивает `status` для затронутого сервиса (или `status all`). Основной ожидаемый формат ответа: `Checking service "issuing-service" ..... running.` — количество пробелов не важно. Для `status all` такая строка должна выводиться для каждого сервиса. Поддерживаются `running`, `stopped`, `failed` и `not running`; также распознаются некоторые другие английские и русские формулировки. Неизвестный формат отображается в таблице как «Неизвестно».

В SSH-консоли показываются обычная команда управления и её цветной вывод. Служебные `printf`-маркеры не отправляются на сервер. Статусы определяются по строкам вывода `status`, который автоматически вызывается после `start`, `stop` и `restart`.

При первом запуске после обновления старая SQLite-база автоматически получит поле общего скрипта. Существующие серверы и микросервисы сохранятся; путь к общему скрипту нужно заполнить в параметрах сервера. Старые индивидуальные пути остаются в базе для сохранности данных, но больше не используются.
